# 架构说明

## 分层

```
浏览器
  ├── WebSocket ──────────────► data-stream.binance.vision   （实时价格，公开数据直连）
  └── HTTP ──► Next.js 服务端 ──► 各数据源                    （K线/指标/资讯/研判）
                    │
                    ├── lib/datasources/   数据源适配器：把各家 API 归一化成统一契约
                    ├── lib/indicators/    技术指标计算（确定性，无 LLM 参与）
                    ├── lib/analysis/      LLM 研判（只在服务端，持有 API Key）
                    ├── lib/alerts/        告警：规则求值 + 常驻轮询 + 通知分发
                    ├── lib/history/       研判存档、结果复用判定、准确率回测
                    ├── lib/forecast/      技术走势预测：不可变存档 + 到期自动复盘（实验性，决策 16）
                    └── lib/steady/        稳健驾驶舱：计划、持仓、风险体检、今日行动（首页，决策 14）
```

服务端还有一条不由浏览器触发的路径：`instrumentation.ts` 在服务启动时拉起
`lib/alerts/worker.ts` 的轮询循环，它自行取数、求值、推送通知，
不依赖任何页面处于打开状态；同一个钩子还拉起 `lib/forecast/worker.ts`，
每分钟用真实行情复盘到期的预测存档（独立于告警开关）。

### 为什么实时行情让浏览器直连，K 线却走服务端

- **实时行情**是公开数据流，不涉及任何凭据。浏览器直连少一跳延迟，
  服务端也不必为每个用户维持一条上游 WebSocket。
- **K 线**要跟着算 20 多个技术指标。放服务端算有三个好处：
  不阻塞浏览器主线程；多个客户端共享缓存；
  最关键的是——图表、指标面板、LLM 研判用的是**同一份计算结果**，
  不会出现三个地方数字对不上的情况。

## 关键设计决策

### 1. 数据源适配器与统一契约

`lib/datasources/types.ts` 定义了 `Candle`、`Ticker`、`DerivativesSnapshot` 等类型，
每个 adapter 负责把自家 API 的原始响应翻译过来。上层只认这些类型。

**为什么重要**：在这个项目里数据源不是稳定的——今天 OKX 能用，
明天可能要换成别家；今天用 binance.vision，将来接了代理可能换回主站。
把差异关在 adapter 里，换源时改动不会扩散。

### 2. LLM 只解读，不计算

所有指标由 `lib/indicators/` 用确定性代码算好，再以格式化文本喂给模型。
Prompt 里明确要求"不要重新计算任何指标"。

**为什么**：模型算数会出错，而且出错时说得同样自信。
让它做自己擅长的事——把一堆事实串成有逻辑的判断、指出信号冲突——
比让它兼职当计算器可靠得多，还省 token。

### 3. 结构化输出

研判结果用 Zod schema（`lib/analysis/schema.ts`）+ structured outputs 强约束，
而不是让模型自由写一段话再解析。看板要把结论渲染成进度条、标签、情景卡片，
自由文本驱动不了 UI。

Schema 里刻意包含 `dataGaps`（数据缺口）和 `risks`（风险）两个必填字段，
逼模型说出它没看到什么、判断可能怎么错——避免只输出一段乐观叙事。

### 4. 供应商抽象：把"能不能连上"和"支不支持强校验"两件事分开

`providers/` 下每家供应商实现同一个接口，`runner.ts` 完全不知道背后是谁。
这层抽象不是为了好看，是被两个现实问题逼出来的：

- **网络可达性因地而异**：Anthropic 官方在中国大陆需要代理，
  DeepSeek 直连可达，中转站则因节点而异。用户必须能换。
- **只有 Anthropic 原生支持 structured outputs**。其余供应商走 `json_object` 模式，
  只保证"是合法 JSON"，字段对不对全靠 prompt 引导。
  所以有 `schema-prompt.ts`（注入格式说明）与 `json-repair.ts`
  （剥代码块围栏、抽出 JSON、Zod 校验，失败时带着具体字段错误重试一次）。

上层看到的始终是一个已经通过 Zod 校验的 `Analysis` 对象。

### 5. 规则引擎与 LLM 并存

`summary.ts` 里有一套透明的加权打分，输出 `bias` 和逐条 `reasons`。
它有两个作用：直接显示在指标面板上（不花钱、不延迟）；
作为 LLM 的输入之一，让模型有个可对照的基线。

用户能同时看到"规则怎么说"和"模型怎么说"，两者分歧时反而是有价值的信号。

**这套权重已经量过了，结论是不该照测得的值改**——见下一节。

### 6. 先量，再决定信不信它

`backtest.ts` 在历史 K 线上逐根重放规则引擎——规则引擎是确定性的，
所以不必像 LLM 研判那样等真实调用积累样本，几千个观测今天就能拿到。

2026-08-21 实测（8 币种 × 1h/4h/1d，22216 个观测，7:3 时间切分）的结论
出乎意料，但正是做这件事的意义：

- 除 RSI 极值外，**趋势类信号在样本上略微反向**（均线排列 -3.3pt、MA200 -2.2pt）
- 规则引擎整体命中率 30.2%，而「无脑全猜震荡」有 51.9%——**跑不赢基线**
- 按实测推出的权重会把 5.16/6.0 压在 RSI 上，表态比例从 79% 掉到 7.4%。
  整体命中率看似升到 51.1%，但那是**沉默换来的，不是预测力换来的**，且仍低于基线

所以权重保持原样，改的是**定位**：规则引擎的 bias 从「方向判断」降级为
「技术面处于什么状态」的透明摘要，prompt 与界面上都如实标注了这一点。

三条由此固化进代码的纪律：

1. **信息量必须减基线**。牛市里「看多」本来就有六成对，
   一个信号只有跑赢该方向的本底出现频率才算有信息。
2. **比较必须对覆盖率免疫**。只看「表态时的命中率」会奖励那些几乎不表态的方案。
   `scorecard` 因此用三分类整体命中率——这个 bug 开发时真的踩过一次。
3. **推权重的数据不能用来验证权重**。按时间 7:3 切分，后 30% 从不参与推导。

`npm run backtest` 与 `npm run backtest:resonance` 可随时重跑。
两个脚本都会自己报告样本的方向偏斜与有效独立样本量——
观测窗口高度重叠时，22216 条观测的有效独立样本可能只有几百条。

### 7. 告警在服务端求值，浏览器只订阅

`engine.ts` 是一组纯函数（输入快照，输出事件），`worker.ts` 负责调度它。
两者分开，使得同一套判定逻辑既能被常驻进程调用，也能被单元测试直接喂数据。

三个容易踩的点，都已经踩过：

- **浏览器端求值必须彻底移除**。两边同时求值会重复触发、通知发两遍。
- **规则必须存服务端文件**。存 localStorage 的话常驻进程根本读不到——
  那这个功能就白做了。旧规则做了一次性自动迁移。
- **worker 状态挂 `globalThis`**。Next.js 把 instrumentation 与 API 路由
  编译进不同模块图，模块级变量在两边是各自独立的副本，
  会导致 `/api/alerts/status` 永远读到初始值、界面误报"未运行"。

代价：告警随服务进程存活。常驻部署见 `docs/DEPLOY.md`。

常驻之后又冒出第四个坑：常驻服务占着 3000 时再敲 `npm run dev`，
**Next 会自动改用 3001 而不是报错**，两个进程对同一份 `data/` 各跑一套轮询、
通知发两遍。所以 worker 启动时要取 `data/alerts.lock`，拿不到就不求值并说明是谁占着。
锁按心跳判定、持有者消失后自动失效——死锁导致「告警彻底不工作却看不出原因」，
比偶尔重复一次通知更糟。

### 8. 研判结果按波动率复用，而不是按固定时长

每次研判是一次真实付费调用（实测 23-95 秒）。`history/cache.ts` 按
(距上次研判时长 + 价格漂移 / 上次 ATR%) 判定是否复用上次结论。

两个关键点：

- 漂移阈值必须**相对标的自身波动率**换算。固定百分比会让低波动币几乎永远命中缓存、
  高波动币几乎永远不命中。
- 缓存判定放在拉 K 线**之前**，命中时把 3 次 K 线请求和 1 次 LLM 调用一并省掉；
  且**命中不写新存档**——同一次研判被计入准确率两次会污染回测数据。

### 9. 每次研判都存档，并自动回头检验

`history/` 把每次研判连同当时的价格与 ATR% 存下来，到期后拉真实行情自动评估。
设计上有两处刻意为之：

- **有效波动阈值由标的自身 ATR 推导**，不是固定百分比。
  否则高波动币会被判成"总是判断正确"（它总在大涨大跌）。
- **永远并排显示"无脑猜同一方向"的基线**。跑不赢基线的模型没有价值，
  这个对比必须自动摆在眼前，而不是等人想起来算。

置信度校准表（"模型说 80 分时实际对多少"）是这里最有价值的产出，
而 `calibrate.ts` 把它**回填到研判结论旁边**——需要主动去翻的表，
在真正需要它的时刻（正看着一条结论、判断该信几分）不会被翻开。

校准用 Beta 后验：先验中心取模型自称的分数，用同区间的历史命中情况更新。
三条原则决定了它不会变成有害功能：

- **没有证据时不做修正**。向模型自称的分数收缩，而不是向 50% 或基线收缩——
  样本为零时校准值等于原分数，表示"暂时没有理由认为你说得不对"。
- **小样本不出数**。少于 10 条已评估记录一律只说"还差几条"。
  2 条样本能算出"校准后 0%"，那个数字和 200 条算出来的看起来一样权威。
- **永远带不确定度**。"41%"像个结论，"41% ± 14%"才诚实。

### 10. 宏观资讯与行业资讯分开存放

美联储数据（`datasources/macro.ts`）没有并进 `news.ts`，两者的 `NewsItem`
带 `category` 字段区分，接口也是分开的。原因是**更新频率差两个数量级**：
加密资讯每小时几十条，美联储讲话几周一条。合并成一个按时间倒序的列表后，
宏观信息会被永久挤到列表末尾并被 `slice` 截掉——接了等于没接。

界面上同理：宏观独立成一个标签页（"查"），行业资讯留在技术面下方（"刷"）；
只有政策利率与议息倒计时被提到图表下方的环境条，因为那是看盘时应该一直在余光里的东西。

**唯一一处 HTML 抓取**也在这个模块：美联储没有提供议息日历的结构化接口。
解析失败时返回空、界面显示"日历不可用"，不做硬编码兜底——
一个过期的议息日程比没有日程更危险。`scripts/test-fomc-parse.live.mjs` 拉真实页面校验解析结果
（`npm run test:live`）。

### 11. 数据源健康检查是一等公民

`/api/health` 和顶部状态条不是运维摆设。在受地区限制的网络下，
"某个源今天通不通"是真实会变的状态。图表空白时用户需要立刻知道
是网络、上游还是代码的问题。同一接口还会探测**服务端出口 IP 与国家**——
Node 的 fetch 默认不读 `HTTP_PROXY`，服务端很可能在用户毫不知情的情况下绕过 VPN 直连。

### 12. 数据源分层：每类判断只认一个来源

详见 `docs/DATA-FRAMEWORK.md`。要点：

- **行情**走 Binance 公开镜像。主站与合约 WS 实测均不可达，衍生品因此留在 OKX——
  这不是偏好，是 `fstream.binance.com` 连不上。
- **数值**走 FRED。净流动性（总资产 − 逆回购 − 财政部账户）比利率水平更贴近加密，
  但三个序列单位与频率都不同，相减前必须归一化——错了不会报错，只会给出错数字。
- **政策态度**只认官方原文。转述会加入解读，而市场逐字读的是原文。
  鹰鸽用词典打分而非 LLM：确定性、免费、可回测，且必然带逐条证据。
- **资讯广度**用 Finlight，但它的免费档不返回实体与情绪，所以它只提供覆盖面，
  不参与判断。

加签那个测试刻意**按官方文档独立重写了一遍签名算法**去比对，
而不是调用被测代码自证——三家的 key/data、毫秒/秒、签名放 URL 还是放请求体
各不相同，正是最容易写反的地方。

告警测试里最要紧的是 `bb_squeeze_release`：它关心的是「上一轮挤压 → 本轮不挤压」
这个**状态转变**，而上一轮快照存在 worker 内存里、重启即丢。
真实行情里没法按需制造这个转变，只能喂快照测；漏了「无上一轮快照时保持静默」
这条，worker 每次重启都会把所有未挤压的币报一遍。

### 13. 常驻进程顺带做低频维护

worker 已经在跑了，再起一套调度纯属多余。所以它除了求值告警，还做两件事：

- **每 15 分钟评估到期研判**。此前这件事只在有人打开准确率面板时才发生，
  也就是说不打开看板研判就永远不会被检验，而置信度校准要攒够样本才出数。
- **每天快照一次 `data/`**。保留 14 份，目录名用日期所以重复调用是幂等的。

两项都自己记上次执行时间，与轮询间隔解耦——用户把轮询调到 20 秒，
不该因此每 20 秒评估一次。任何一项失败都只记日志：
维护任务不该拖垮告警这个主职能。

worker 还会自己喊话：启动时发一条上线通知（顺带验证通道配对了没有），
连续 3 轮失败发一条中断告警、恢复时再发一条。
告警的全部意义是「你不用盯着」——那么它自己停摆时，
更不该指望用户主动打开页面去发现。

## 数据存储

全部是 `data/` 下的 JSON 文件，不入库（`.gitignore` 已排除）：

| 文件 | 内容 | 写入方 |
|---|---|---|
| `analyses.json` | 研判存档与评估结果 | 研判接口、历史接口 |
| `alert-rules.json` | 告警规则 | 规则接口、worker（更新触发时间） |
| `alert-events.json` | 已触发事件 | worker |
| `steady.json` | 投资计划与手填持仓（**用户手填，丢了只能重填**） | 驾驶舱接口 |
| `forecasts/<id>.json`、`<id>.evaluation.json` | 技术预测的原始记录（连同输入快照，不可覆盖）与到期复盘结果，每条预测两份文件 | 预测接口、预测 worker |
| `alerts.lock` | 告警单实例锁（按心跳判定，持有者消失后自动失效） | 告警 worker |
| `backups/` | 以上数据的每日快照，保留 14 份 | 常驻 worker、`npm run backup` |

单人本地工具，文件足够；上数据库属于过度设计。前三个文件的写入都做了串行化——
Next.js 路由并发处理，worker 也在并发写，两边同时 read-modify-write 会丢数据。
`steady.json` 用原子写（临时文件 + 重命名），`forecasts/` 用硬链接原子发布且从不覆盖；
两者遇到损坏的文件都**报错而不是当成空数据**——悄悄丢掉的财务数据与复盘依据，比一次报错更糟。

## 成本

除 LLM 外，全部数据源免费无 Key。研判为手动触发（不自动轮询），
单次调用输入约 2-4K token，按 Claude Opus 5 定价约 $0.02-0.05/次；
命中缓存则为 0。

第二个 LLM 调用点是**资讯 AI 汇总**（`/api/news/digest`）：它在面板挂载时就会请求，
靠进程内缓存控成本（默认 20 分钟，`NEWS_DIGEST_TTL_MINUTES`；面板上的「重新汇总」可跳过缓存）。
这也是 ROADMAP v2「雷达页请求合并」要处理的点。

### 14. 稳健驾驶舱：风险优先，且是第一份财务数据

产品的北极星是小白的稳健收益。回测已多次证明方向预测没有稳定优势，所以这一层**不预测任何价格**，
只做两类可以诚实算出来的事：

- **历史回放**（事实，但样本只有已有那段历史）与**情景压力**（假设，不是预测）。两者在界面上分开标注——
  币安日线只能回溯约 2.7 年，覆盖不到真正的熊市，只看回放会系统性低估风险。
- **由用户的底线反推配置**，并留 20% 安全垫：熊市基准（BTC -75%）本身是假设，正好踩线的配置一旦现实略差就破线。

三个值得记住的取舍：

1. **持仓手动录入，不接账户**。延续「只读公开行情」的边界；对稳健目标，每月改一两次持仓足够。
2. **持仓是项目里第一份财务数据，所以多了三层保护**：`guard.ts` 只接受回环 Host、拒绝跨站请求
   （常驻服务会跟着笔记本连咖啡馆的 Wi-Fi，此前「监听全部网卡」只关乎被刷额度，现在关乎隐私）；
   文件 0600；损坏时改名留档而不是覆盖（history/store.ts 的「损坏就当空」在那里合理，在这里会抹掉唯一一份手填数据）。
3. **取数可部分失败**。币安镜像走代理时会抖，风险体检不该因为一个币没取到就整页报错；
   取不到的写进「数据缺口」，其余照算。

计算层（`risk.ts` / `plan.ts` / `actions.ts`）刻意不依赖任何取数或文件模块，客户端建计划时的实时检查
与服务端的权威计算用的是同一份函数。

访问范围默认只限本机。确需在手机上看，设 `STEADY_ALLOW_LAN=1`——它只放开 Host 检查，跨站检查仍在；
代价是同一局域网的人也能读到持仓，所以默认关（见 `.env.example`、DEPLOY.md）。

### 15. 行情源：快速失败、互为回退，且整体故障不伪装成空数据

币安镜像与 OKX 的 REST 请求统一 **6 秒超时、适配器里不重试**。原因是路由层（`market.ts`）手里有第二个源：
在同一家上重试会让一次故障多等 2~3 倍的时间，快速失败、立刻换一家才是更快的路。
回退成功时返回值里带着**实际来源**，界面据此标注；成功的来源会被沿用 60 秒，避免每次请求都先撞一次坏源。

几条由此固化的纪律：

1. **整体故障不能伪装成空数据**。`fetchTickers` 全部失败时抛出真实错误（以前是 200 加空数组）；
   OKX 返回错误码时抛错（以前是空数组）；K 线进入指标之前先过 `validateCandles`
   （价格为正、高低开收自洽、时间严格递增），坏数据停在入口，不会算出一个看着正常的错指标。
2. **失败归因看主源**。两家都失败时，错误以**主源**的失败为主、注明回退源也没成，状态码与 `cause` 也取主源的。
   以前抛的是最后一次（回退源）的错误：币安超时、OKX 又不认识该交易对，用户只会看到 OKX 报错，然后去查 OKX。
   `http.ts` 的归一化同样保留底层 `cause`，并把三种失败分开说：超时；连不上（带底层错误码——
   `ECONNREFUSED` 通常是代理没开，`ENOTFOUND` 是 DNS，`ECONNRESET` 是被掐断）；
   收到了但不是 JSON（多半是 WAF 或验证页，说成「连不上」会把人带偏）。
3. **需要「不被缓存、不被合并」的快照时要显式声明**。同参数的并发请求默认合并成一次上游调用；
   生成预测传 `fresh` 绕开缓存与合并。复盘用 `fetchCandleWindow`，**固定回到原交易所**取窗口内的实际 K 线
   （单次最多 100 根）——拿另一家的数据去检验这一家的预测，等于换了尺子。
4. `isGeoBlocked` 只认 451。403 可能只是 WAF 或访问策略，说成「地理封锁」会把排查带偏。

另一半在部署：服务端出站请求默认全走代理，而币安镜像直连稳定在 1 秒内、经代理会抖到超时，
所以 `setup-launchd.mjs` 把它自动并入 `NO_PROXY`（见 DATA-SOURCES.md、DEPLOY.md）。

### 16. 技术走势预测：先存档、后复盘，不把它当作预测力的证据

`lib/forecast/` 是一套**启发式**情景生成器（均线趋势、MACD 动量、RSI 与布林带的均值回归、量能、吞没形态），
七个图表周期各自独立计算，只使用生成时已收盘的行情。它不是训练出来的模型：参数标注为「尚未经样本外校准」，
任何调参都必须升级 `MODEL_VERSION`。规则来源与局限见 [TECHNICAL-KNOWLEDGE.md](TECHNICAL-KNOWLEDGE.md)。

设计的重心在**事后能被检验**，而不是预测本身：

- **每条预测连同输入快照存成不可变文件**（`data/forecasts/<id>.json`）：先写临时文件，再用硬链接原子发布，
  跨进程竞争也不会覆盖已有预测；同一收盘锚点去重；权限 0600。存档损坏时**报错**，不当成空历史——
  与驾驶舱存储是同一个原则。
- **到期自动复盘**（`worker.ts`，每分钟，独立于告警开关）：回到原交易所补齐窗口内的实际 K 线，
  算方向命中、收盘 MAPE、情景范围覆盖，并与「所有未来收盘 = 最后已收盘价」的朴素基线比较
  （相对基线改善小于 0，就是不如不预测）。缺行情或未到期则保留「待复盘」，不计为错误；
  单轮最多处理 20 条、4 路并发，失败的旧记录不会永远霸占名额。
- 不同模型 / 知识库版本的统计互不混用，历史记录保留以供审计。

这与决策 6 是同一个态度：**先量，再决定信不信它**。2026-10-14 取证时的小样本（27 条）方向命中 25.9%、
相对基线 −25.6%（见 PRODUCT-STRATEGY §1.4），所以它保持「实验性」，不进首页、不参与驾驶舱的任何计算。
已知的扩展性隐患（非阻塞）：每分钟全量读取所有存档、每日备份全量复制 14 份。

注意与 `lib/indicators/forecast.ts` 区分：后者是主图下方的**趋势预判表**（历史类比 `analog-v1`，
24 小时 / 7 天 / 60 天三个窗口，披露观测数与不重叠窗口数），不存档、不复盘。

### 17. 研判链路：一个次要字段不该作废一次 30~150 秒的付费响应

`/api/analysis` 的失败有三类，处理原则不同：

- **取数阶段**（`errors.ts` 的 `withRetry`）：取行情失败时静默重试一次（间隔 0.6 秒）；仍失败就按**实际数据源**
  命名（币安镜像 / OKX）报错。研判最贵的是后面那次模型调用，不该死在前面一次网络抖动上；
  次数刻意很少，真断网时不让用户干等。
- **模型阶段**：供应商层按失败类型区别对待——输出被 **max_tokens 截断**时把上限翻倍（封顶 32000）再试并记录
  `finish_reason`，与**空内容**分开处理；**校验失败**带着具体字段错误重试一次，重试以 `retry` 事件告知界面
  （重试等于再等一整轮模型推理，不说的话看起来就是卡住了）。`levels.invalidation` 因此可缺省——
  它的缺失曾是校验失败的大头，评估与上图本就跳过非有限值；提示词仍要求必须给出。
  模型错误被翻译成「发生了什么 + 该做什么」（鉴权 / 404 / 限流 / 超时 / 网络）。
- **传输阶段**：流必须以 `done` 或 `error` 收尾，`error` 带 `code` 与 `retryable`。前端见到流在两者之前断开，
  按失败处理并给「重试」，而不是让按钮悄悄恢复。客户端中途断线时服务端照常跑完并落盘，再点一次直接命中缓存（决策 8）。

最常见的一个根因在部署而非代码（币安镜像被代理拖到超时），见决策 15 末段与 DEPLOY.md。
这些路径由 `scripts/test-analysis-resilience.mjs` 钉死；provider 的重试流程用本机假端点验证，不碰真实模型。
